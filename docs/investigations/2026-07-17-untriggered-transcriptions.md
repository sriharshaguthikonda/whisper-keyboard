`"Starting recording..."`, but nothing upstream of it produces a `record_key_event` line — so the
log looks like 100% of recordings appeared out of nowhere, when in fact the trigger key was
consumed by the broker, not silently invented by python. **This is a real historical
gap in observability, not proof of phantom triggers** — but it also means the pre-07-12 window
cannot be further analyzed from `wkey-runtime.log` alone (see Suggested next tests).

The 2026-07-13 (36%) day is the transition day; from 2026-07-14 onward the rate is a clean 0%.

### 3. Kanata chord config: shared key between two chords, both bound to common home-row letters

`C:\Tools\kanata-runtime-repo\vd-toggle.kbd`:

```
(defchordsv2
  (d f) @df-voice 65 first-release ()
  (s d) @sd-voice 65 first-release ()
)
```

`df-voice` = `(tap-hold 100 100 @df-typed f23)`, `sd-voice` = `(tap-hold 100 100 @sd-typed f13)`.
Both chords require a 180ms typing-idle pause (`chords-v2-min-idle 180`) then a 65ms co-press
window, then distinguish a 100ms hold (→ F23/F13) from a quicker release (→ restore typed
letters). **"d" and "f" are directly adjacent, extremely common home-row letters** (used in
"find", "different", "hard", "used", "second", etc.), and "d" is shared by both chord
definitions. A brief hesitation with a finger resting on "d"/"f" after any 180ms pause in typing
(reading, thinking, switching windows) is enough to complete the gesture. This is a highly
plausible, well-supported mechanism for the F23 misfires seen in finding #2 — kanata sends a
genuine-looking F23, python logs a genuine-looking `press_start`, and nothing in the current
logging pipeline can tell the two apart.

Notably, `f13` (the S+D "ask-AI" chord) is **not wired into python at all** —
`grep -r 'f13|F13' wkey/` returns zero matches, and `SUPPORTED_RECORD_KEYS` in
`faster_whisper_Mother_of_all_wkey.py:486-491` has no `'f13'` entry. So the S+D chord is currently
a no-op in python, but its presence still makes kanata arbitrate two overlapping chord
definitions that both consume the "d" key — a plausible (unproven from these logs; kanata does not
log to `wkey-runtime.log`) contributor to F23's chord-decomposition timing.

  (none since), e.g.:

  This is the pre-fix singleton correctly blocking a second manual/task launch while one was
  already running (task + manual double-start). **It stopped happening after the 2026-07-12
  P1 fix** — consistent with the reclaim-capable singleton (`acquire_runtime_singleton`,
  `faster_whisper_Mother_of_all_wkey.py:3496-3549`) doing its job.
- **0** genuine `reclaimed_stale_runtime_lock` events (all 12 raw hits were pytest fixture noise) —
  the reclaim path has not needed to fire in production since shipping.
- Currently exactly **one** whisper-keyboard python process is alive (pid 11512, started
  2026-07-17 15:30:24, `backend_health_status.json` heartbeat current). No concurrent instance
  found in `Get-CimInstance Win32_Process` at investigation time.

Separately worth flagging: unit tests that exercise `acquire_runtime_singleton` write their

## Hypotheses, ranked

1. **(HIGH confidence) Kanata D+F chord misfires during normal typing.** Since the 2026-07-12/13
   fix, 100% of recording starts have a logged trigger key, and 78% of those are F23. Python's
   logging cannot distinguish an intentional chord from an accidental one — both look identical.
   `d`/`f` are common adjacent home-row letters; the 100ms hold-vs-tap heuristic is easily
   satisfied by ordinary typing hesitation.
2. **(LOW–MEDIUM, unproven from these logs) Shared "d" key across two chord definitions
   ((d f)→F23 and (s d)→F13) perturbs kanata's own chord arbitration**, possibly making F23 more
   likely to fire on sequences kanata is deciding between. Cannot be confirmed without kanata's
   own debug/verbose log (kanata does not write to `wkey-runtime.log`).
3. **(Historical / informational, not currently actionable) Pre-2026-07-12 100%-"unexplained"
   period is a broker-era observability blind spot**, not evidence of a python-invented phantom
   trigger — the broker owned the physical key and never logged to `record_key_event`.
4. **(RULED OUT for the current window) Duplicate/concurrent backends.** Singleton lock works;
   only 1 process alive now; genuine double-start rejections stopped after 2026-07-12.
5. **(RULED OUT for the current window) Audio-overflow-triggered restarts causing phantom starts.**
   No overflow/resume event precedes any post-07-14 start without an accompanying real keypress.

## Recommended logging identifiers (file:function)

- `wkey/faster_whisper_Mother_of_all_wkey.py:start_recording` (line 2136) — the
  `"Starting recording..."` log line currently carries **no pid, no session id, no keyword_index**,
  even though `current_recording_session_id` and `keyword_index` are already in scope at that
  point, and `stop_recording` (line 2271) already logs all three for the *stop* side. Add
  `pid=%s session_id=%s keyword_index=%s` to this one line — this is the single highest-value,
  lowest-cost change: it turns "grep one timestamp, get the whole session's identity" into reality
  instead of requiring a join across multiple log lines.
- `wkey/keyboard_shortcuts.py:_log_record_key_event` (line 166) — has action/key/recording/
  suppression/active-keys/pressed-keys, but no backend pid (the class has no `os` import). Add
  `pid=os.getpid()` for correlation against multiple historical/overlapping runs in the same file.
- `wkey/faster_whisper_Mother_of_all_wkey.py:start_listener` (line 2907-2911) —
  `Listener(on_press=on_press, on_release=on_release)` passes **no `win32_event_filter`**, so there
  is currently no way to tell a kanata-synthetic (`SendInput`-injected, `LLKHF_INJECTED`) F23 apart
  from a genuinely separate physical key delivering the same VK. Add a `win32_event_filter`
  callback that reads the raw message's injected flag and thread it through to
  `on_press`/`on_release`/`_log_record_key_event` as `synthetic=True/False`. Note this will very
  likely show 100% of F23/F13 events as injected (kanata always synthesizes them) — its value is
  ruling out a second, non-kanata source of F23, not distinguishing intentional-vs-misfired kanata
  chords.
- `wkey/keyboard_shortcuts.py:on_press` (line 42-90) / `map_key_to_keyword_index`
  (`faster_whisper_Mother_of_all_wkey.py:731-741`) — the *resolved route* (`TRIGGER_ROUTES.get(label)`)
  is computed but not logged at press time; only the raw key is. Add `route=%s` to
  `_log_record_key_event` so a single grep on a `press_start` line shows key, route, and (once #1
  above lands) session id together.
- Kanata itself does not write to any file this investigation could find (no log redirection in
  the running `kanata_windows_gui_wintercept_cmd_allowed_x64.exe --cfg vd-toggle.kbd` command
  line). If chord-arbitration behavior needs verifying, kanata's own verbose/debug output would
  need to be captured separately and time-correlated with `wkey-runtime.log` — currently there is
  no way to see kanata's chord decision-making at all.

## Suggested next tests

1. Land the `start_recording` logging fix above (pid/session_id/keyword_index on the "Starting
   recording..." line) — near-zero cost, immediately makes the next recurrence's grep trivial.
2. To test the chord-misfire hypothesis directly: capture kanata's own log (redirect stdout/enable
   verbose logging in `kanata.bat`/the scheduled task) for a day and cross-reference F23 emission
   timestamps against actual keystrokes typed at that moment — if F23 fires immediately after
   ordinary words containing "d"/"f", that confirms the misfire mechanism.
3. Consider whether the D+F chord's hold requirement (currently 100ms) should be raised, or
   whether the shared "d" key between the two chords should be eliminated by choosing
   non-overlapping keys for the S+D "ask-AI" trigger before it gets wired into python.
4. Fix the test-hygiene issue separately: `test_runtime_singleton_retries0` and friends should not
   let `logging` fall through to the real `ACTIVE_RUNTIME_LOG_PATH` during pytest runs — it
   pollutes the production log and makes any future forensic pass have to re-derive the pytest
   filter done here.
5. Nothing here suggests killing or restarting the live backend (pid 11512) — it was left
   untouched and its heartbeat is current as of this investigation.
